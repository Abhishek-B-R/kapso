# Findings

**1. P1 — The Codex isolation rule is written where Codex's project layer probably is not anchored, and nothing live or in a test shows it refusing anything.**
`src/kapso/execution/coding_agents/adapters/codex_agent.py:276-278` writes `.codex/rules/kapso-campaign.rules` into the directory `initialize()` receives, and `:347` trusts that same path. For the engine's own Codex sessions that directory is `tempfile.TemporaryDirectory(prefix="kapso-inference-")` (`src/kapso/core/cli_inference.py:104`), deleted with the session; for an implementation session it is `session.session_folder`, a gitignored subdirectory *inside* the candidate's clone (`experiment_session.py:171`), so the git top level Codex resolves a project from is the clone root, not the session folder — the rule file would sit below the project root and the `projects."<session_folder>"` trust key would not match it either. The evidence confirms the gap rather than the mechanism: both isolation artifacts report `"codex_rules_files": []` (`scripts/redesign/runs/wp7/{claude_code,codex}/artifacts/isolation.json`), and the step itself only `rglob`s under the campaign (`scripts/redesign/plugin_proof.py:865`) where a temp-dir file can never appear; `tests/test_campaign_session_isolation.py:38` asserts the file's bytes and nothing about enforcement. The plan's provenance claim — "the mechanism WP2 verified" (`docs/plans/redesign/wp7-plugin.md:254`) — matches no record: `prefix_rule` appears nowhere in the repo but this adapter, and `execpolicy` nowhere but wp7's own plan and DECISIONS. Since this rule is the *only* thing the design puts between a Codex campaign session and a nested `kapso build` (Codex has no per-session plugin switch), it should not merge unverified. Fix: confirm the directory Codex anchors a project at for a session whose cwd is a subdirectory of a git repo, write the rules file there (and trust that path), and add one live check — `codex exec` in such a workspace asked to run `kapso build --help`, asserting the refusal — to the isolation step, with the rules-file path reported from where it is actually written.

**14. P2 — `--stop` signals a process group it never checks it owns.**

# What came out clean

- **The campaign gate's contract.** The argv it builds, the receipt's keys, the three refusals (no `kapso` on PATH, brief-and-goal both or neither, inside a campaign), `--json` passthrough with the exit code, a malformed receipt raising, `sys.executable -m kapso.cli` with the server's cwd, config via `GateConfig` and nothing from the environment — all match the frozen Interface and are tested against real shapes, including a real MCP client listing the tools from a server started in a bare directory (`tests/test_campaign_gate.py:154`).
- **`host_only` and the server's always-connect.** `get_mcp_config` raises by name for a host-only gate, `prepare_host_gates` needs nothing for `campaign`, the "nothing to serve" exit is gone, and the instructions compose the staged intro plus one line per gate that is off — with the proof showing both hosts displaying them and making a bank read.
- **`experience.session_sources`.** The type refusal, the per-source degrade with the `add` line, `--experience` staying strict, the explicit empty string, and the project-config discovery rule are implemented as specified and tested (`tests/test_host_session_server.py`).
- **`kapso harness export`.** Union by `listed()` in first-occurrence order with real duplicates in the fixture, `${PLUGIN_ROOT}` expanded, `KAPSO_HARNESS_ROOT` in each server's env, hooks and module pages excluded *and said*, the person's `CLAUDE.md`/`AGENTS.md`/`settings.json` never written, every destination checked before any write, the whole export refused by name on one collision, an unknown host refused — with the strongest test file in the diff.
- **The detach helper's generalisation.** Build keeps its receipt and three-line handoff; learn and ingest get a log beside the target, the learning handoff and no receipt; `--detach` on an instant `add` is refused by name.
- **The trigger suite's construction.** 111 cases at exactly the 60/40 split the plan names, pinned model/runs/turns/tools, "none" cases asserted to contain no mention of Kapso, the refusal patterns shown to discriminate the six skills and to count a skill's own commands — and the Claude Code bar genuinely met (build 19/20, harness 20/20, kapso 20/21, review 19/20, setup 20/20, holdout 10/10, no `not-*` grader tripped).
- **CLAUDE.md compliance in the engine code.** The only `try/except` added is `campaign_gate.py:29-35`, byte-for-byte the sibling gates' MCP import guard; no `os.environ`/`getenv` reads in any new engine path (the gate takes `cwd` and `config_path` as params); no function-local imports in `src/`; `stop_grace_seconds` and `session_sources` live in `config.yaml` and are read through `load_config` at the call site, with `_BUDGET_BLOCK_KEYS` updated; the new tests assert on real artifacts, subprocess argv and a live server rather than on mocks.
- **The six skills against the CLI.** Every fenced and inline `kapso …` line in the skills and commands parses against `build_parser()`, carries `--config kapso-config.yaml` where the verb takes one, and the facts I spot-checked against the code hold (`--all`, `--stop`, `--detach`, `--resume` refusals, `STALLED` as three missed beats, trace's pinned JSON keys, `kapso-evaluation` invoked by name despite being hidden from the menu, which the transcripts confirm on all four build steps).
- **The pages.** `docs/reference/cli.mdx` (`--stop`, `harness export`, both `--detach` lines, `kapso-mcp`'s config rule), `configuration.mdx` (both keys), `mcp-gates.mdx` (the campaign row) and `installation.mdx` are accurate against the code, including the grace key's real home and the degrade policy.
