# Findings

## The harness/task split

**1 — P1 · Changes 4 and 6: two copies of the sanitizer, two copies of the leakage-audit rule table.**
Change 4 ships `sanitize-cache` with `scripts/sanitize.py` ("the handler's `build_sanitized_cache` as a CLI") and `leakage-scan` with `scripts/scan.py` ("the handler's `_audit_patterns` over a diff"), while change 6 keeps `RelBenchHandler`'s "raw and sanitized caches" and "`final_evaluate` (test once, then the audit)". `final_evaluate` *is* `_audit_code` over `_AUDIT_PATTERNS`, and the caches are `sandbox.build_sanitized_cache`. So after the port there are two sanitizers (226 lines in the skill, 361 in `sandbox.py`) and two near-identical regex tables (I diffed them: eleven of the twelve rules are the same patterns with reworded reasons). This is exactly the drift bug class CLAUDE.md rule 1 exists to kill, and rule 7 forbids the dual path.
*Fix:* decide one home per artefact and say it. For the audit: the rule table becomes one data file (JSON/YAML) that the skill's `scan.py` reads and the handler's audit loads from `harness.path`, or the handler's audit is deleted and verification owns it (the harness's verification session already voids on the scan's evidence). For the sanitizer: see finding 2 — one of the two callers must go.

**2 — P1 · Interface ("The evaluation directories") + change 4: the sanitized cache cannot be both `prepared/` and the runner's.**
The port mapping puts the sanitized cache in the setup page ("`sandbox.py`: … return it as `prepared/cache`"); change 6 keeps it on the handler. The two placements are not interchangeable:
- `prepared/` is **not** integrity-verified. `docs/reference/harness.mdx` says the engine "verifies that `kapso_evaluation/` and `kapso_datasets/` are unchanged" after setup — `prepared/` gets no such check. Moving the physical leakage boundary from `kapso_datasets/` to `prepared/` trades a verified directory for an unverified one.
- The setup session's timeout is `harness.setup_minutes` (20, clamped by the budget). A fresh sanitize of a medium database, and all 56 snapshots of the rolling cascade, do not fit 20 minutes, and today the cache is reused across campaigns from `work_dir` with a version marker.
*Fix:* keep the sanitized cache with the runner, passed as `data=`, built before launch as today; the `sanitize-cache` skill becomes a page sentence pointing at the task's data reference, or is dropped. If the owner wants it in setup instead, the plan must raise `setup_minutes` for this harness, state how the cache is cached across campaigns, and ask WP2 for a prepared-resource hash check.

**3 — P1 · Change 14 + Interface: `kernel-slots` as an MCP server has no home for its ledger, and its limits are not the statement's.**
Three distinct problems in one sentence of the plan ("the ledger under the campaign root, the limits from the statement's quota file the setup session writes under `prepared/`"):
- **Blocking.** `kernel_slots.py acquire` *blocks until granted* ("a wait is backpressure, not failure"). As an MCP tool it is bounded by `harness.server_tool_timeout_seconds` (600 s packaged). With 2 GPU slots and K=8 lanes, waits beyond ten minutes are normal, and the tool call will be killed mid-queue.
- **The ledger's path.** A harness server runs with the *session* directory as `cwd`; `KAPSO_HARNESS_ROOT` and `${PLUGIN_ROOT}` point at the read-only harness; `prepared/` is a symlink and read-only by the harness's own hook. There is no harness-visible variable for "the campaign root", so a ledger shared by eight sessions has nowhere to live in the grammar WP2 shipped.
- **The limits.** `gpu: 2 / cpu: 5 / ttl / reap_interval / verify_timeout / aging` live in `benchmark.session_budget.kernel_slots` (rule 1: config-like values belong in the config). They are **Kaggle's per-account interactive-session limits**, not the task's submission quota — RULES.md keeps them in separate sections, and the statement's quota (default 50 submissions) is a different quantity. Sourcing pool sizes from "the statement's quota file the setup session writes" conflates the two *and* lets an agent author its own limits.
*Fix:* keep the pool sizes in the config and thread them to the server as an `env` entry or a staged file the runner writes (not a session); give the server an absolute ledger path from the same source; and decide explicitly whether `acquire` stays a path-invoked CLI (my recommendation — it already is, it is stdlib-only by design, and blocking is its contract) with the harness contributing only the `kaggle-cli`/economics skill that names it. If it must be a server, add a non-blocking `claim`/`poll` pair and say what the timeout is.

**4 — P1 · Interface ("The trees") + change 3: `requirements.txt` pins the benchmark's library on a domain harness, so every build refuses without it.**
The on-disk `predictive-modelling/requirements.txt` is `relbench>=2.1.2, pyarrow, duckdb, pandas, numpy`. `check.requirements()` tags every requirement row with **all** modules, and `build()` raises `HarnessError` on unmet needs of `BUILD_MODULES` (`kapso.py:1296`). Consequences: (a) change 19's "Kaggle tabular competition … with `--harness predictive-modelling`" refuses before any session unless relbench is installed on that machine — the swap cannot be "zero edits"; (b) every user who installs the wheel sees `kapso harness list` report the bundled harness as needing relbench; (c) the harness that is supposed to be domain-general declares a benchmark dependency.
*Fix:* `requirements.txt` holds only what the harness's *own* scripts need for every task (the scan needs nothing; the sanitizer needs relbench). Either drop `sanitize.py` from the harness per finding 2, or move the relbench pin out of `environment.python` and have the skill's text say "needs the task's own library, which the task statement names" — a need `check` reports through the hook/server program path, not as a blanket requirement.

**5 — P1 · Change 11: ALE's "task root with statement, scorer, cases and baseline" has no owner, and today no scorer CLI exists.**
Change 11 puts "setup: the task root with statement, scorer, cases and baseline" on the **setup page** and ships a `scorer-cli` skill ("how to run the scorer the task root provides") plus a `require-scorer-run` Stop hook. But today the official scorer is `ale_bench`'s `session.public_eval(code)` — a Python call the *handler* makes out of band, averaged over `RUN_COUNTS = 4` — and the handler's prose tells the agent to "implement a small input generator and scorer exactly per the problem statement's specification". So: there is no scorer binary in a task root; a setup session that builds one is an agent writing its own evaluator; and change 12 ("the grader over the public cases through the Docker scorer") does not list the work of materialising statement + scorer + seeds + baseline into the task root.
*Fix:* make it the runner's work, listed as such in change 12 (`data=` the task root it writes from `ale_bench`), and reword change 11's setup page to "read the task root the task statement points at". Separately, say where `require-scorer-run` learns the seed count: reading it from the agent's own results file makes the hook forgeable, and hard-coding it is a benchmark constant.

**6 — P1 · Interface ("The evaluation directories") + change 9: MLE's in-loop grade would optimise against the private answers.**
The plan: "MLE: a grader directory the runner writes per competition, which runs the candidate under the runtime limit and grades it with MLE-bench's grader against answers that live outside the workspace." Today the in-loop score is deliberately **not** that: `MleBenchHandler.run` reads the candidate's own `<score>` tag from its self-carved 10% holdout, and `grade_csv` is computed only to set `got_medal`; the official grade is `final_evaluate`. Feeding `grade_csv` into the search makes the private test the search signal — a different (and much weaker) experiment, and the bar "a valid graded score at the budget" would then be a test-set number.
*Fix:* the grader directory runs the candidate and prints **the candidate's held-out score** (the contract MLE's prose already states: "stratified … 10% of the training data for test and train nothing on it"), or the runner writes a real split and grades on it. `mlebench.grade_csv` stays in `final_evaluate`, scored once. Say this in the Interface line, because the current wording reads as the opposite.

## The runners on `build()`

**11 — P1 · Interface ("The runners") + changes 6, 9, 12: the metric's direction has no home, and one of the four chosen tasks is lower-is-better.**
`GenericProblemHandler.maximize_scoring = True`, hard-coded, and `build()` constructs that handler; `Brief` has no direction field — "measured by: the metric and its direction" is prose for the agent only. The strategy reads `maximize_scoring` in six places (parent choice, pruning, the cost estimator, the checkpoint). `spooky-author-identification` (change 10) is scored by multi-class log loss: **lower is better**. So are the RelBench NMAE/MAE tasks (the swap in change 19) and ALE's `ahc025`/`ahc027` (the "problem outside the lite list" in change 19).
*Fix:* decide now that **the evaluation directory emits an oriented score** (higher-is-better, e.g. the negated or complemented metric) with the raw metric beside it in the manifest and the orientation stated in the Brief's `Measured by` — and say so in the Interface, since each grader must then do the flip and the final report must undo it. The alternative (a direction on the Brief or a config key) is a WP1/WP4 interface change and needs the owner.

**12 — P1 · Changes 6, 9, 12, 15: four engine-facing handler behaviours lose their home silently.**
`ProblemHandler` carries `maximize_scoring` (finding 11), `honor_agent_stop`, `deliverable_ready_reserve_seconds()` and `finalize_run_selection()`; the orchestrator reads all four. None has an equivalent on `build()`, and the plan never mentions three of them.
- `honor_agent_stop = False` is IOAI's "hard guarantee" against the judge voting stop — its comment records a rehearsal that "ended the campaign 25 min early" at 0.982. RelBench gets the same effect through `campaign.py`'s `--knowledge-file` carrying `NO_STOP_NOTE` — a channel the plan deletes with `extra_knowledge`.
- `finalize_run_selection` is what stamps a judged-**invalid** archived run. Without it, `select_final` falls back to `infer_session_finals`, which can only promote *pending* runs to `final`/`superseded` — it cannot mark one invalid. So a voided or integrity-flagged run becomes eligible for `final_evaluate`: precisely the incident the handler's docstring names ("the user-ignore incident shipped a self-disqualified leaky intermediate").
- `deliverable_ready_reserve_seconds` releases IOAI's insured reserve once a public score is banked.
*Fix:* add a change that settles each: the open-ended-goal rule as a line in the Brief's rules *and* a stated config/engine seam if prose is not enough (WP4 owns the budget's end — ask it); `final_evaluate` driven from `Solution` (its rejected/void candidates) rather than from the raw archive, or the runner passing an exclusion set; and a decision on whether WP4's "derived and bounded reserve" already replaces the insured reserve.

**13 — P1 · Interface ("The evaluation directories"): nothing exports the RelBench grader's seven environment variables.**
`data/generic_eval/grader.py` calls `_env()` and `sys.exit(2)` for `RELBENCH_DATASET`, `RELBENCH_TASK`, `RELBENCH_PRIMARY_METRIC`, `RELBENCH_WORK_DIR`, `RELBENCH_FULL_TIMEOUT`, `RELBENCH_DEBUG_TIMEOUT`, plus `RELBENCH_CACHE_DIR` and optionally `RELBENCH_ROLLING_ROOT`; its README says "All configuration arrives via environment variables exported by the RelBench handler before the search starts". The plan says only "`evaluation=data/generic_eval`". If the handler is no longer in the prompt path, who exports them — and does a session-spawned evaluation inherit them? (CLAUDE.md rule 3 is about *our* config, so this is not a rule violation, but it is an unstated dependency on process-wide state.)
*Fix:* say it: the runner writes a per-task grader directory (as change 9 already does for MLE) whose entrypoint reads a committed `task.json` beside it, and the env-var contract is deleted. That also makes the evaluation directory self-describing and fingerprintable, which the integrity rule wants.

**14 — P2 · Interface ("The runners"): flags the rewrite drops that `campaign.py`, the harvest and the maintainer depend on.**
The four CLI lines show only `-s/-t`, `--harness`, `--experience`, `--time-budget-hours`, `--coding-agent`. Today `campaign.py` invokes `benchmarks.relbench.runner` with `-i`, `--workspace` **and** `--knowledge-file`/`--target-val`, then harvests the trajectory from that workspace path; `runner.solve_task` also seeds `initial_repo` with a trivial `main.py` because "the maintainer calibrates the registered evaluation at setup, which requires a runnable candidate — and `parent_policy=best` needs a real starting parent"; `--resume` is what the plan's own GPU-preemption risk relies on. None of `repo=`, `output=`, `resume=` or `budget.experiments` appears in the Interface.
*Fix:* write the full mapping in the Interface — `-i`→`Budget.experiments`, `--workspace`→`output`, `--resume`→`resume`, the seeded baseline→`repo`, `--target-val`/`--knowledge-file`→ (deleted, with the no-stop rule rehomed per finding 12) — and state what `campaign.py` has to change ("`campaign.py` follows" is too thin for a file whose arguments are the contract).

**15 — P2 · Changes 9 and 15: the two per-round dynamic signals become static.**
`MleBenchHandler.get_problem_context(budget_progress)` recomputes the stage line every round ("** Current Stage is FINAL ENSEMBLING **"), and `KaggleNotebookHandler` injects `_remaining_str()`. `kapso_task.md` is composed once ("by the engine and never by a session"). Change 8's "the three stages as a pacing rule by budget progress" assumes the session can read its own budget progress.
*Fix:* name where a session reads remaining budget and spend (the evaluation output's run/budget notes? the status file? the session prompt?) and verify it in the proof run; if nothing carries it, that is a finding for WP4/WP6 to be raised now, not after the arms.

## The IOAI book as a bank

**16 — P1 · Interface ("The IOAI book as a bank") + change 16: the card grammar's evidence block does not admit third-party evidence.**
`Card.conformance_findings` requires a **non-empty** `evidence` list whose every entry's `verdict` is one of `confirm | weaken | refine | refute | spawn | exercise`, and the real shape of an entry (fixture `bank_seed`) is `source: {learner_run: lr_…, trajectory: …, ref: file#L104-L116, card_version: n}`, `verdict`, `usage` ("Never served (the bank was empty) …"), `effect` (measured numbers). Every one of those fields describes **what a kapso campaign did with the claim**. A curated winner solution has no learner run, no trajectory, no line-range ref, no usage and no effect — only someone else's public score. The plan's "the evidence block naming the public score and its source" has nowhere legal to sit: the conversion must either invent measurement-shaped entries (which the retriever and the graders then price as ours) or extend the grammar — and `src/kapso/learning/bank.py` is owned by neither WP8 nor WP3 in this plan.
*Fix:* owner's decision, before building: (a) add a `reported` source kind and a non-executed verdict (say `reported`) to the card schema, excluded from `EXECUTED_VERDICTS` and from reliability promotion — a small, honest change to `bank.py` that WP8 must request; or (b) keep the book out of the bank grammar and serve it as an ingested index after all (the original port-mapping plan), accepting the ingest cost; or (c) convert only the entries where **we** ran the solution and have a trajectory, and leave the rest as the local book. Do not let the conversion script write evidence it does not have.

**17 — P2 · Change 16: the conversion's file list is short of what the grammar and the readers need.**
The plan writes "`index.md`, `insights/`, `procedures/<uid>/card.md` …, `log.md`" and tests "`index.md` listing the cards". But: `Bank.conformance_findings` requires **`insights/index.md` and `procedures/index.md`**, each listing every card by name (the top-level `index.md` is not read for coverage); `init_bank`'s founding skeleton also writes `sightings.md`; `is_bank` requires a git repository whose **`main`** branch holds `index.md`, `insights/`, `procedures/` (so the script must `git init -b main`, add and commit — the plan never says the output is a repository, only that its "home is `~/banks/ioai-book.git`"); and per card the ledger needs `type`, `scope`, `evidence`, `reliability.{state,rationale,plain}`, `log` with **`len(log) == provenance.version`**, a non-empty body whose `**Rule:**` paragraph yields a hero, `representation: code` for a procedure that ships code, plus `probe`, `supersedes`, `contradicts`. `Card.parse` *raises* on a card without the format-v2 `---` + fenced-yaml ledger — and it raises at **serving time, mid-campaign**, because load only runs `is_bank`.
*Fix:* list the exact file set and ledger keys in the Interface, make the script `git init -b main`+commit, and make change 16's test assert `Bank(out).conformance_findings() == []` rather than "every card field the grammar names" — that is the only check that will actually catch a malformed card before the IOAI arm.

**18 — P2 · Interface + "Not in scope": the provenance reading is the right basis but is missing four questions.**
"A source's stated licence and the organizers' rules" is the correct pair, and keeping anything unknown local-only is right. What it does not answer, per entry:
- **No stated licence is the common case.** A Kaggle notebook carries a licence only if its author chose one; absent one it is all-rights-reserved. The table needs "unstated" as a first-class verdict that maps to local-only, not a blank.
- **Use versus redistribution are different questions.** The organizers' rules bind what we may *use in a run*; a licence binds what we may *publish*. The local-only bank is still used in runs, so each entry needs both verdicts, not one.
- **The "ours" line.** A reimplementation written from a public write-up is ours; one with copied code is a derivative. Define the bright line (no copied code, idea only, cited) or "ours" will absorb the hard cases.
- **Third-party payloads inside `solution/`.** Checkpoints, scraped data samples and vendored files carry their own licences and, for a 35 MB tree, their own risk. The pass must cover the files, not only the write-up.
*Fix:* make `PROVENANCE.md`'s columns: entry, source URL, stated licence (or "unstated"), use-verdict, publish-verdict, third-party payloads, our-reimplementation yes/no. The owner then decides the remote with that table, as the plan already says.

## The abstraction scan

**19 — P1 · Interface ("The abstraction scan") + change 18: the gate test's vocabulary comes from imports the gate does not have.**
"the words are … read from the benchmarks' own registries (RelBench's `task_specs`, ALE's problem lists, MLE's competition registry, IOAI's practice uids)". Of the four: `benchmarks/relbench/task_specs.py` imports nothing heavy and works ✓; **ALE's lists live inside `benchmarks/ale/handler.py`, which does `import ale_bench` at module level**; **MLE's registry is `from mlebench.registry import registry`**; **IOAI has no registry at all** (its override file holds `run_defaults`, not a task list — see finding 23). `tests/test_benchmark_runners.py` guards each with `pytest.importorskip`, which tells you these packages are not assumed present. A gate test that skips is not a gate.
*Fix:* move ALE's problem lists into a dependency-free module beside `task_specs.py`; derive the MLE and IOAI vocabularies into a committed data file with a separate, skipped-when-absent test that the file still matches the registry; then the scan's gate test runs unconditionally.

**20 — P1 · Interface ("The abstraction scan"): the two fixed rules are both too lax and too blunt, and the file scope is unstated.**
- **Too lax.** "A decimal that reads as a score, quota or deadline" misses every integer: `50` submissions, `2` GPU / `5` CPU sessions, `266` packages, a kernel-run cap in seconds, `40` evaluation timestamps. And the vocabulary (task/dataset/competition/problem names) would not catch `relbench`, `AHC`, `kaggle`, `NvidiaTeslaT4`, `RELBENCH_CACHE_DIR` — so the leakage-scan script, which is nine-tenths benchmark constants, scores zero hits.
- **Too blunt.** The tree *already* contains six decimals: `relbench>=2.1.2` and `pandas>=2.0` in `requirements.txt`, `version: 0.1.0` in the manifest, and `0.8` / `0.95` in `cv-protocol` and `relational-feature-practices` — the last two being the measured-noise thresholds the design explicitly wants on a skill. `MODELLING_PRACTICE_NOTE` carries a dozen more (`0.005`, `0.01`, `0.92-0.94`, `0.98`, `p>0.5`).
- **Scope.** The plan never says whether `scan(root, …)` reads pages only, pages + `SKILL.md`, or every file including scripts and `requirements.txt`. That choice decides the whole result.
*Fix:* state the scope (my recommendation: pages and `SKILL.md` bodies, excluding fenced code blocks, excluding `requirements.txt` and `harness.yaml`); replace "a decimal" with "a number adjacent to a quota/deadline/score word" plus an allow-list of statistical thresholds and version strings; and add the library/benchmark names (`relbench`, `mle-bench`, `ale-bench`, `ahc`, `kaggle`) to the vocabulary with a decision on which are permitted domain vocabulary (`write.mdx` allows API names) and which are not.

**21 — P2 · Interface ("The abstraction scan"): the "foreign path" rule collides with the harness's own content.**
The conventions listed are `${PLUGIN_ROOT}`, `$KAPSO_HARNESS_ROOT`, `prepared/`, the task statement. But `living-documents` is specified to carry the table-information and feature-history templates, which live in `$KAPSO_SHARED_CACHE_DIR`; the rolling contract names `$RELBENCH_CACHE_DIR` and `$KAPSO_RUN_DATA_DIR`; `results/` is called "the harness's own convention" in `write.mdx` but is not in the plan's list.
*Fix:* decide whether `$KAPSO_SHARED_CACHE_DIR` and `results/` are harness conventions (I think the shared cache must be, or `living-documents` cannot say where its files are — and that is a question for WP4, which owns the parameter), add them to the rule, and keep `$RELBENCH_*` as a hit, which then forces findings 1 and 7.

**22 — Clean, with one caveat · keeping `check` domain-agnostic is right.** `check` reads one harness and cannot know whose task names matter; a user's harness is not our benchmark's. The DECISIONS entry argues it correctly. The caveat: say in `docs/harnesses/write.mdx` that the scan exists and is ours, so an author does not expect `check` to catch a task value — `write.mdx` already states the rule ("A page never holds a value that belongs to one task") with no enforcement behind it.

## The reproductions

**23 — P1 · Change 7 + Risks: the noise band has no source in the tree, so the acceptance line is unfalsifiable.**
