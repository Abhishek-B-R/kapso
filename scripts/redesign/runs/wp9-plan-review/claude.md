## Findings

**1 · P1 · Change 1, Acceptance, S6.** The second "fail-loud case" is not fixed: `_run_role_for_artifact` already ran the role twice before the change (`_run_role`, then `_run_role` again, then the caller's `read_text()` raised); the commit only improved the message. The round's actual cause is visible in the archive: the learn failed **one second** after the exam phase opened (`learn-status.json`, 04:00:34 → 04:00:35), and `graders.crew.report_writer`/`assessor` are `cli: codex, model: gpt-5.6-sol` on a machine whose Codex key answers `Quota exceeded` on every session (`isolation.json`). So the learn still cannot complete on the fresh machine, and S2's `learn-complete` and all of S6 inherit that. *Fix:* name the cause in the plan; decide where the learn runs (a box with Codex quota) or put the grader roles' models to the owner as a decision — swapping models to make a run pass is the owner's call, and the record must say so; make the acceptance a measured learn of WP7's archive that banks ≥1 card, not two unit tests.

**2 · P1 · S5, `evaluator-crash`.** The plan reuses WP6's injection, which WP6 itself recorded as the wrong shape: the implementer session absorbed the one-shot `RuntimeError` and the engine's own evaluation never met it — "the engine-side crash stays for WP9's S5 to inject differently". *Fix:* inject where the engine's frame run reads it (crash on every invocation, or a marker the engine's own evaluation meets), and pin the `expect` as the attempt's `evaluation.output`, the judge's rejection and the status's state.

**3 · P1 · S5, acceptance.** The driver as described is mechanical (`inject`/`expect` over the status and inbox), but the acceptance counts *user messages* and requires a *diagnosis naming the class and the fix* — both need a host session in the loop and an author. *Fix:* per injection, name the host, the user (scripted or persona), who diagnoses (the operating skill), and define a user message as one user turn; ≤2 is then countable.

**4 · P1 · Change 3, the persona.** `--user persona:<card>` "for every answer" cannot replace three scripted policies: `harness-new` needs the six trading module answers (`HARNESS_ANSWERS`) that no listed card carries; `inbox` needs the driver's out-of-band act (writing the key *before* the person says so — WP7's own finding); the criteria steps need "stop here: do not launch". *Fix:* state per step what the persona is given (card + the step's intent) and which steps keep their driver actions, and add a trading persona — otherwise the interview degrades to "use your best judgement" and the step measures nothing.

**5 · P1 · S1 and the persona prompt.** Both are handed the example's `README.md`, which teaches `kapso build …`, `Solution.open`, `kapso deploy` and the recorded 0.8474. That contradicts the `ml-engineer` card ("has never used Kapso or read its docs") and leaks S1's answers into the arm that is supposed to measure whether the docs are enough. *Fix:* give both a de-Kapso'd task view (`repo/` plus a task README with no Kapso lines and no recorded result), as the driver already writes for `build-data-only` and `build-empty-wish`; the example README stays for readers.

**6 · P1 · S1.** Tasks 4–6 (deploy the result, learn from it, resume a killed run) need a delivered campaign and a killed one; the plan gives each attempt "the churn fixture and nothing else", and the released arm cannot be handed a redesign-era campaign (different record). *Fix:* say what each task starts from, built per arm by that arm's own package, and put that build time in the hours.

**7 · P1 · Runner, Risks.** The machine's Codex key is over quota, so S1's Codex arm, S4's Codex reader, the author test's Codex author and S2's Codex half all fall to the development box — exactly the contamination the design forbids ("never the development box, so nothing the development checkout happens to have can make a flow look smoother"). The plan concedes it only for S2. *Fix:* decide now — a Codex credential with quota, or state per test which arm ran where and mark every dev-box arm's smoothness numbers advisory.

**8 · P1 · Scope.** WP7 deferred nine things to "WP9's round"; the plan picks up two. Missing: the command→skill handover read as the procedure; the handoffs' tighter form (the 13/16/15-line overruns); the interview's silent module (ask vs say); the inbox fixture service that answers the key **and the continuation that uses it**; the review near-misses' turn cap; the second engineer's served build; a staged card for the empty-bank read; the stop→resume continuation (PR review, Claude 5); the machine's examples dependencies. *Fix:* a "what WP7 deferred here" section, each item answered or re-deferred with a reason.

**9 · P1 · Record and report.** The record shape is built for a conversational round and the five new tests do not fit it: `report.py` reads `step["messages"]`/`completed` unconditionally (KeyError on an S1 attempt step), `step_passes` **fails** any step the budgets do not know (so twelve S1 attempts × 4 arms each need a budget entry), `test_semantic_report.py` forbids budget keys outside the four limit keys (so `first_try`, `wrong_calls`, the anytime gap and the guess count have no home), and the judge's new `{model, scores}` shape breaks the existing dimension table — "it already renders `judge`" is only true of the old flat mapping. *Fix:* decide the shape now — one step per task with a per-step `metrics` dict, a `judge: {vendor, model, scores: {dimension: {score, evidence}}}` sub-record, the bars in one place the renderer reads, and the judge's bar reflected in the run's verdict (acceptance says "every dimension at 4 or above"; nothing computes it).

**10 · P1 · The author test.** "Zero structural guesses after the guide's fixes, each guess a sentence added to the guide" cannot be shown in one round, "structural" is undefined, and the plan never says this is the re-run of WP2's test (2026-10-25: 66 and 65 guesses, the guide revised the same day). By WP2's grammar a "guess" includes domain judgment ("guide section 8 should explain when a metadata-only state server is sufficient"), which will never reach zero. *Fix:* define a structural guess (a field, file, key, convention or host behaviour the engine or `check` would reject if guessed wrong) against a domain choice, have the judge classify each line, record both counts beside WP2's 65/66, and budget two rounds per author. Also say the author may not run `check` itself (WP2's rule) and that the new fixture changes the inputs, so the counts are not comparable to WP2's.

**11 · P2 · S4.** No campaign is named, and Q3 ("what was voided, on what evidence") and Q4 are vacuous unless the record contains a void and a rejection — both WP6 readings answered "nothing voided", one "nothing rejected". *Fix:* name the campaign (the trading build under the harness, with an integrity/void injection from S5, or WP7's archived churn build) and require a void and a rejection in it.

**12 · P2 · S4, acceptance, `s4.md`.** "Answered correctly" is well defined for Q1/Q3/Q4/Q5 (extractable facts) and not for Q2 ("why") or Q6 ("safe to merge") — WP6 graded those as "defensible", with the real criterion "no claim wrong against the record". *Fix:* the rubric scores Q1/3/4/5 against the extracted facts, and Q2/Q6 on two tests: every cited fact checks out against the record and the conclusion names its evidence. That, plus the quote-must-re-grep rule, is what keeps the judge on the facts rather than its own reading.

**13 · P2 · S1, `first_try`.** Undefined for both surfaces. *Fix:* the counted call is the first execution of the task's verb (`Kapso.build(...)` / `kapso build …`); `--help`, `doctor` and docs reads do not count; `wrong_calls` counts errored executions of that verb only; "within one step" means the next execution of the same verb. Without this the 9-of-12 bar is not reproducible between runs.

**14 · P2 · S1, the sandbox.** "Nothing else" is not enforced. A session with web access finds the published (pre-redesign) docs; a machine with the plugin installed carries the six skills, i.e. the answers. *Fix:* a plugin-free, server-free session with no web, over a directory holding `docs/` and the task view, proved from the session's init event the way the isolation step does.

**15 · P2 · S1, the baseline.** "The released wheel and its docs" — the released docs are not in this tree (Rule 7 rewrote them in place). *Fix:* name the source (a checkout of the released tag's `docs/`, or the live site, pinned by date), and say per task whether 0.7.10 has the verb at all; otherwise "9/12 vs n/12" reads as a usability comparison while measuring feature presence.

**16 · P2 · `s1.md`.** Three questions carry the judge's items but not the design's comprehension grading ("what did each call do, what did it return, where is the record", bar: correct on every verb), and the two mechanical counts (the Python flow in twelve lines, the CLI in six commands) are recorded nowhere. *Fix:* the rubric holds the comprehension key per verb; the two counts are metrics, not judge opinions.

**17 · P2 · S6, Consumed.** There is no status history: `OperationStatus._write()` replaces the file atomically and `recent` is a short ring. *Fix:* derive the anytime series from the checkpoint's node history (`started_at` + `duration_seconds` + `score`), or sample `watch --json` at `budget.checkpoint_heartbeat_seconds` and archive the samples. The same sampling is what makes S5's "truthful within one heartbeat" measurable — say where the cadence comes from (the config, not a literal).

**18 · P2 · S6, soundness.** At one build per arm, the gap is dominated by whether an attempt happened to land: the same fixture delivered 0.8450, 0.847, 0.8508 and nothing twice across WP1/WP4/WP6/WP7, and ideation alone took 28 of 60 minutes, so "a tiny budget" delivers nothing and the budget must be ≥60 min. *Fix:* state the bar as a smoke bar with the observed spread recorded, say the claim it supports is "the served cards were read and cited" (the design's own hedge), and state what the learn must produce for the test to mean anything: ≥1 banked card, in a scope the second build is served, read beyond `indexed_only`, and named load-bearing in the trace.

**19 · P2 · S5, the shim.** `claude` is resolved by name, so a PATH shim works — but the engine also runs `shutil.which("claude")` and `claude auth status` in the preflight, and `--version` in the doctor. A shim that fails those stops the launch instead of the session. *Fix:* pass through everything but a session turn, keep the count in a file, and state what "handled" means given that the engine has no rate-limit path at all (the session fails, the record says so, the campaign continues) — otherwise the class passes or fails vacuously.

**20 · P2 · S5, the full disk.** A tmpfs at the campaign directory also breaks the status writer, which writes its temp file into that directory (`mkstemp(dir=self.path.parent)` + `os.replace`). The plan's own risk says "the engine's own status writer must survive the write failure to say so" — it cannot, without the `try/except` CLAUDE.md forbids. *Fix:* decide where the truth is reported when the campaign directory is full (the parent's log and the launch receipt, which `watch` already reads), and size the tmpfs so the data/evaluation writes fail first if the status must keep writing.

**21 · P2 · The judge, Interface.** `--judge <vendor>` on `plugin_proof.py` (which runs on the machine) contradicts "the judge runs on the development box over fetched transcripts". *Fix:* make `judge.py` a standalone pass over a fetched record directory. That also makes the JSON-or-fail contract cheap — the right contract, but only if a malformed reply costs one model call rather than a day of machine time; and pin the extraction rule (exactly one JSON object, or the bridge's JSON mode) so the run does not fail over a code fence.

**22 · P2 · The judge, input.** `judge(rubric, transcript_paths, …)` implies feeding stream-json whole; a three-hour round's streams will not fit a context window, and Rule 6 forbids trimming them on the way in. *Fix:* the judge reads the rendered conversation (the user's messages and each turn's final text — what the rubric actually grades, as WP7 settled), windowed per step with one call per step and the frame aggregating. Say it in the plan.

**23 · P2 · The judge, fallback.** "The vendor that did not play either side" does not exist in any arm: with Claude Code as host and Codex as user (and the reverse), both vendors have played. *Fix:* name the real fallback — a second Gemini route (the restricted key), or the run is reported unjudged with the hard metrics standing, or a stated same-vendor judge marked as a weakness.

**24 · P2 · The judge, single pass.** Acceptance gates on "every dimension at 4 or above" from one reply. The house practice for graded labels is two blind passes with a third adjudicating disagreements. *Fix:* two passes; a dimension whose passes straddle the bar is adjudicated or reported as straddling, with the budgets (messages, questions, minutes, lines) as the binding bar and the dimensions as evidence.

**25 · P2 · Change 2, the persona driver.** `next_message(...) -> Optional[str]` returning `None` for "done" cannot be distinguished from a user-side CLI failure (quota, timeout, empty output) — a 429 on the persona's account would read as a satisfied user and the step would look complete. *Fix:* fail loud on a non-zero exit or empty reply; `None` only for a reply that is `DONE` alone. For comparability also pin and record: the user model and effort, both CLI versions, the per-step turn cap, mechanical patience (the driver turns the persona terse after `patience` questions rather than hoping the model does), the card's sha256, the prompt template's sha256, the fixture commit and the wheel's sha. With those in `user: {kind, card, card_sha256, vendor, model, prompt_sha256}` the record tells a persona run from a scripted one; `test: S2` vs `S2-mechanical` alone does not.

**26 · P2 · The persona as a stand-in.** It is sound on vendor independence and turn-by-turn pressure, and unsound exactly where S2's rubric lives: a model user is never bored, never abandons, reads a forty-line message happily, and tends to say "go" to a wrong proposal. *Fix:* plant one step whose proposal carries a deliberate error and assert the persona pushed back (the design's "sometimes wrong, sometimes changing its mind"); if it does not, the persona arm is advisory for "not annoying" and "engaging" and the plan should say so.

**27 · P2 · Change 1, the mining repair.** The plan says "the validator hands a document that does not parse back to the crew"; the code can only recognise the one shape the round found (a regex over frontmatter lines), because detecting "does not parse" needs the `try/except` Rule 2 forbids. *Fix:* say that in the plan (the general form is not implementable), and state the residual risk: the next unparsable shape still ends an hour-long learn — mitigated by naming the file and the line and by the mined view being regenerable with `--force`.

**28 · P2 · Runner.** `fresh_machine_install.sh` installs uv, Node, the two CLIs and the wheel — not the fixtures' dependencies, and not `duckdb`/`dbt-core`/`dbt-duckdb` (which the example now pins). WP7's finding asked WP9's provisioning to do it. *Fix:* install them as a uv venv first on PATH, with the example's pins.

**29 · P2 · Risks, hours and spend.** No hours or dollars per test, and the machine's default `--max-run-duration` is 4h while S2 alone is ~3h per host plus install, and S6 is two ≥60-minute builds plus a learn. *Fix:* hours, dollars and `KAPSO_FRESH_MAX_RUN` per test (WP7's trigger suite alone was $26.81), plus the token-window gate per arm — and note that the persona's side consumes the same account's window as a Claude host.

**30 · P2 · Tests.** Earning their place: `test_learning_repairs` (fail-loud paths), the fixture contract test, the S1 predicates, the judge's JSON and quote-re-grep contracts, the no-clip prompt test (it pins Rule 6), the S6 arithmetic, the S5 shim counter. Weak as written: "the rubric's rendering" (a template interpolation) — make it assert the rubric *is* the design's (five dimensions by name, six questions, three S1 questions), a drift check; and "the vendor's CLI call is the other vendor's" is near-tautological but cheap and pins the design rule. Two gaps: build the S1/S5 predicate fixtures **from the archived WP6/WP7 transcripts**, not hand-written shapes (the question detector was wrong three times against real streams), and extend `test_the_budgets_cover_every_step_of_the_round` to the new drivers' step names so a missing budget is caught before a three-hour run, not in the report.

**31 · P2 · Scope vs Ownership.** Scope allows a one-line fix in a merged package; Ownership says `src/kapso/**` beyond the two learning files is read, never edited. *Fix:* bound the exception (which files, which kinds of line) or drop it.

**32 · P2 · Archive.** The plan archives records, transcripts and reports but not the judge's prompt, raw reply and the extracted facts — without them a verdict cannot be re-checked. *Fix:* archive them beside the record (one file per run, as the plan already says).

**33 · P3 · Interface.** `next_message(card, task, history, host_message, vendor)` has no parameter for the fixture README the prompt is said to carry — name it (`task` = the fixture directory, the README read from it).

**34 · P3 · Interface, personas.** `data-engineer` is described as "S1's second persona", but S1 as specified runs no persona and one fixture. Either S1 gets a second fixture arm (the dbt example) or the card's role is the author test's reader alone.

**35 · P3 · Size.** The sub-plan says L; MASTER's table says M, spread. Reconcile one of them.

**36 · P3 · Knobs.** Six new drivers will each carry models, bars, caps, the shim's N and the tmpfs size. `budgets.json` cannot hold them (its test restricts the keys). *Fix:* one constants module (or one `suite.json`) the drivers and the renderer read, and the record echoes.

## What came out clean

- The vendor triangle: user from the other vendor, judge from a third — and Gemini on Vertex from the development box is a real third vendor, reachable where the credit project is.
- The JSON-or-fail judge contract and the evidence-must-re-grep rule: the right principles, and Rule 2-shaped (given finding 21's separation of the judge pass).
- Parking S3's non-regression and abstraction with WP8, and placing the author test here: both match MASTER's dependency line.
- The four planned decisions in DECISIONS.md are the right ones to have taken now (the persona over a bespoke API client, the scripted policy kept behind `--user scripted`, `trading-strategy` = `examples/trading` and `empty-wish` written by the driver, the shim's honesty).
- `examples/pipeline-dbt` as built meets the fixture contract: thirteen assertions in four seconds, the metric as the last line, `result.json` in the engine's shape, a non-zero exit with the reason, a seeded byte-identical generator with `MANIFEST.json`, `--fast` marked not comparable, and the baseline in both the brief and `baseline.json`.
- The mining colon case is genuinely fixed and pinned by a test that asserts the finding's text and that a quoted reference parses.
- S6's citation claim is readable from what exists: the trace already carries each attempt's cards `read`, `listed` and `load_bearing`, and the lessons block carries `read_by` and `load_bearing_by` per source.
- The Risks section is honest where it matters (the shim is not a real limit, the persona's variance with the transcript kept whole and one re-run recorded, the judge's vendor, the learn's repairs possibly not being small).
- Archiving one file per run under `runs/wp9/<test>-<host>/` with the report under `tests/semantic/reports/`, and keeping transcripts whole.
