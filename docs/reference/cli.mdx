Kapso installs the `kapso` executable with ten commands, and `kapso-mcp`, the MCP server that serves Kapso's knowledge and experience tools to the coding-agent session you work in (see [below](#kapso-mcp)).

| Command | What it does |
|---------|--------------|
| [`kapso build`](#kapso-build) | Build software that meets a brief, by experiment |
| [`kapso harness`](#kapso-harness) | Author, check and fetch harnesses: the domain layer a build loads |
| [`kapso research`](#kapso-research) | Deep web research for an objective |
| [`kapso learn`](#kapso-learn) | Trajectory learning: import, mine, grade, update, codify |
| [`kapso deploy`](#kapso-deploy) | Deploy a solution as running software |
| [`kapso index_kg`](#kapso-index-kg) | Index a knowledge graph from a wiki or JSON |
| [`kapso watch`](#kapso-watch) | Watch a running operation |
| [`kapso inbox`](#kapso-inbox) | What a paused campaign is waiting on you for, and the reply that resumes it |
| [`kapso bank`](#kapso-bank) | Manage the lesson bank's share remote |
| [`kapso doctor`](#kapso-doctor) | Check this machine can run what your config asks for |

## Global options

| Flag | What it does |
|------|--------------|
| `-h`, `--help` | Show help for the command and exit |
| `--list-agents` | List the available coding agents with their models and install commands |

```bash
kapso --list-agents
```

On a standard install the six agents are `claude_code`, `codex`, `gemini`, `openhands`, `oss_claude_code` and `vertex_claude_code`; the legacy `aider` extra registers a seventh.

## kapso build

Runs an experiment campaign that meets a brief and returns the solution; writes it to `<output>/.kapso/solution.json` too. See [The brief](/docs/build/brief) and [Run and watch](/docs/build/run-and-watch).

| Flag | What it does | Default |
|------|--------------|---------|
| `--brief` | The brief file (`kapso-brief.md`): objective, how it is measured, baseline, target, rules, budget. Mutually exclusive with the two below | — |
| `-g`, `--goal` | The objective in a sentence. A resume takes it from the checkpoint | — |
| `-f`, `--goal-file` | A file holding the objective as plain text | — |
| `--evaluation` | Directory holding your evaluator; copied to `kapso_evaluation/` and protected | — |
| `--data` | Directory holding your data; copied to `kapso_datasets/` | — |
| `--repo` | The starting repository, a local path (copied) or a GitHub URL (cloned) | — |
| `--harness` | The [harness](/docs/harnesses) to build with: a bundled name, a directory, or a git reference. Wins over the brief's `Harness` line; checked before anything starts, and an unmet need of the build's modules refuses with its fix | the brief's `Harness` line, else none |
| `-o`, `--output` | The campaign directory, the solution's trace. Empty for a fresh build | a temporary directory |
| `--budget-minutes` | Wall-clock budget for the campaign, durable across resumes | — |
| `--budget-experiments` | Maximum experiments this call may run. A resume keeps the launch's cap | `10` |
| `--budget-usd` | Best-effort model-spend budget in USD | — |
| `--budget-reserve-minutes` | Wall clock escrowed for the final checkout and evaluation | — |
| `--resume` | Continue the campaign in `--output` from its checkpoint. The brief and every launch flag come from the checkpoint and launch record; pass only what changes, such as a bigger budget | off |
| `--detach` | Start the campaign in a session of its own and return at once with its pid, the log, the status path and the `watch` command. Needs `--output`. The run outlives the shell that started it, a coding agent's tool call included | off |
| `--log` | Where a detached run's output goes | `<output>.log`, beside the campaign directory |
| `-m`, `--mode` | Config mode: `GENERIC` or `MINIMAL` | from config (`default_mode`) |
| `-a`, `--coding-agent` | One of `claude_code`, `codex`, `gemini`, `openhands`, `oss_claude_code`, `vertex_claude_code` | from config |
| `--config` | Config path | the packaged `config.yaml` |
| `--kg-index` | Path to a `.index` file for knowledge search | — |

A budget flag wins over the brief's `Budget` line; on a resume the launch record fills what is still unset.

```bash
kapso build --brief kapso-brief.md --evaluation evaluation --data data --repo repo --output campaign --detach
kapso build --harness ./harnesses/trading --brief kapso-brief.md --evaluation evaluation --data data --repo repo --output campaign --detach
kapso build --goal "Build a web scraper for news articles" --output ./scraper
kapso build --goal-file problem.txt --budget-experiments 20 --output ./campaign
kapso build --output ./campaign --resume --detach
```

When a session needs something only you can provide, the campaign pauses: the summary block says `WAITING ON YOU` instead of `COMPLETED`, the exit code stays 0, and [`kapso inbox reply`](#kapso-inbox) resumes it. See [the inbox](/docs/build/inbox).

## kapso harness

Author, check and fetch harnesses, the domain layer a build loads: one directory per domain holding instruction pages, skills, tool servers, delegates and hooks, listed per module in `harness.yaml`. See [Harnesses](/docs/harnesses) and the [harness reference](/docs/reference/harness).

| Subcommand | What it does |
|------------|--------------|
| `new` | Write the two-file starter for a new harness: `harness.yaml` and `instructions/guardrails.md` |
| `check` | Check a harness: failures, warnings, and what this machine lacks |
| `add` | Fetch a git reference into the store and check it; a directory is checked in place |
| `update` | Re-fetch a branch or `HEAD` reference; a tag or a commit never moves |
| `remove` | Delete one fetched clone, every harness in it; a directory is refused |
| `list` | The bundled and fetched harnesses, each `ready`, with what it needs, or failing check |

A reference is a bundled name (`trading`), a directory (`./trading`), a git URL (`git+https://github.com/acme/harnesses@v3#trading`) or GitHub shorthand (`acme/harnesses@v3#trading`). Every subcommand but `new` takes `--config` for the config whose `harness.store` is the store.

### kapso harness new

| Argument | What it does | Default |
|----------|--------------|---------|
| `name` | The harness name, `[a-z0-9][a-z0-9-]*`. **Required** | — |
| `--dir` | The parent directory | the working directory |

```bash
kapso harness new trading
```

### kapso harness check, add, update and remove

| Argument | What it does | Required |
|----------|--------------|----------|
| `ref` | A bundled name, a directory, or a git reference | **yes** |

```bash
kapso harness check ./trading
kapso harness add acme/harnesses@v3#trading
kapso harness update acme/harnesses@main#trading
kapso harness remove acme/harnesses@v3#trading
```

`check` and `add` print the report: a summary line such as `check ok (7 skills, 2 agents, 2 servers, 6 hooks)`, then one line per `fail`, `warn` or `needs`, then the harness's name and version. A failure exits 1; what the machine lacks never does.

### kapso harness list

```bash
kapso harness list
```

## kapso research

Runs deep web research and writes structured findings.

| Flag | What it does | Default |
|------|--------------|---------|
| `--objective` | Research objective | — |
| `--objective-file` | File containing the objective. Mutually exclusive with `--objective` | — |
| `--mode` | `idea`, `implementation` or `study`. Repeat the flag for more than one | `idea` and `implementation` |
| `--depth` | `light` or `deep` | `deep` |
| `-o`, `--output` | Output file for results, as JSON | — |

```bash
kapso research --objective "How to optimize transformers?"
kapso research --objective "LLM fine-tuning" --mode idea
kapso research --objective "RAG implementation" --mode idea --mode implementation
kapso research --objective-file topic.txt --mode study --depth deep
```

## kapso learn

Trajectory learning. Ten subcommands cover importing finished campaigns, mining them, grading a bank, and folding results back in.

| Subcommand | What it does |
|------------|--------------|
| `import` | Import archived campaign tarballs into the trajectory store |
| `mine` | Mine store-resident trajectories into their derived `mined/` views |
| `grade` | Grade a bank against held-out trajectories, or one arriving trajectory |
| `update` | Run the update crew: fold mined and graded trajectories into the bank |
| `init-bank` | Create the bank home: a bare repo plus the founding skeleton |
| `develop` | Run one learner version through the development regime |
| `codify` | Run one codify request, which is a build minus ideation, against the bank |
| `ingest` | Operating-regime chain for one campaign: mine, exam, lesson |
| `gauntlet` | Run the duplicate and stability traps against a completed development run |
| `behave` | Run behavior scenarios as semantic production tests |

Every subcommand takes `--config` to point at a config other than the packaged `config.yaml`.

### kapso learn import

| Flag | What it does | Required |
|------|--------------|----------|
| `--subset` | Subset YAML of `trajectories: [{id, archive, role}]` | no |
| `--archive` | One archive URI or path ending `.tgz` | no |
| `--id` | Trajectory id override, used with `--archive` | no |
| `--no-upload` | Skip remote upload even when one is configured | no |

```bash
kapso learn import --subset docs/plans/learning/d1-subset.yaml
kapso learn import --archive gs://bucket/runs/campaign/20260731T092629_lane-a2.tgz
```

### kapso learn mine

| Flag | What it does | Required |
|------|--------------|----------|
| `--trajectory` | One trajectory id | no |
| `--all` | Mine every un-mined imported trajectory | no |
| `--force` | Regenerate even when already mined | no |

```bash
kapso learn mine --all
```

### kapso learn grade

| Flag | What it does | Required |
|------|--------------|----------|
| `--bank` | Bank checkout directory | **yes** |
| `--bank-head` | The graded bank head, as an `lr_` tag or a sha | **yes** |
| `--split` | Split manifest, for full mode | no |
| `--learner-version` | Learner version under exam, for full mode | no |
| `--trajectory` | One trajectory id, for exam mode | no |

```bash
kapso learn grade --bank ./bank --bank-head lr_042 --split splits/d1.yaml
```

### kapso learn update

| Flag | What it does | Required |
|------|--------------|----------|
| `--learner-version` | Crew version identifier | **yes** |
| `--batch-manifest` | YAML list of `{trajectory, hindcast_report}`. Omit for docket-only consolidation | no |
| `--split` | Split manifest. On development runs this asserts batch and held-out are disjoint | no |

```bash
kapso learn update --learner-version v3 --batch-manifest batch.yaml
```

### kapso learn init-bank

Creates the bank home. Takes only `--config`.

```bash
kapso learn init-bank
```

### kapso learn develop

| Flag | What it does | Required |
|------|--------------|----------|
| `--split` | Split manifest | **yes** |
| `--learner-version` | Crew version identifier | **yes** |

```bash
kapso learn develop --split splits/d1.yaml --learner-version v3
```

### kapso learn codify

| Flag | What it does | Required |
|------|--------------|----------|
| `--request` | Request YAML naming the card, fixture, materials and gates | **yes** |

```bash
kapso learn codify --request requests/card-117.yaml
```

### kapso learn ingest

| Flag | What it does | Required |
|------|--------------|----------|
| `--trajectory` | Trajectory id in the store | **yes** |
| `--learner-version` | Crew version doing the lesson | **yes** |

```bash
kapso learn ingest --trajectory rel-hm-user-churn-a2 --learner-version v3
```

### kapso learn gauntlet

| Flag | What it does | Required |
|------|--------------|----------|
| `--learner-version` | Completed development run to trap | **yes** |

```bash
kapso learn gauntlet --learner-version v3
```

### kapso learn behave

| Flag | What it does | Required |
|------|--------------|----------|
| `--scenario` | One scenario directory | no |
| `--all` | Run every scenario | no |

```bash
kapso learn behave --all
```

## kapso deploy

Turns the solution a build wrote into running software.

| Flag | What it does | Default |
|------|--------------|---------|
| `campaign` | The campaign directory a build wrote; its `.kapso/solution.json` is the solution. **Required**, positional | — |
| `--strategy` | `auto`, `local`, `docker`, `modal`, `bentoml` or `langgraph` | `auto` |
| `--env` | Environment variable as `KEY=VALUE`. Repeat for more than one | — |
| `--coding-agent` | Agent behind the selector and adapter sessions | from config (`deployment.coding_agent`) |
| `--model` | Model that agent is asked for | from config (`deployment.model`) |
| `--harness` | The harness whose deployment module the selector and adapter sessions carry: the build's, from the campaign record, or another version of it | the campaign record's |
| `--interactive` | Keep running after deploy instead of returning | off |

```bash
kapso deploy ../churn-build
kapso deploy ../churn-build --strategy docker
kapso deploy ../churn-build --env API_KEY=xxx --interactive
```

## kapso index_kg

Indexes a corpus into the knowledge graph and writes a `.index` file that campaigns load with `--kg-index`.

| Flag | What it does | Default |
|------|--------------|---------|
| `--save-to` | Path to write the `.index` file. **Required** | — |
| `--wiki-dir` | Wiki directory to index. Mutually exclusive with `--data-path` | — |
| `--data-path` | JSON data file to index | — |
| `--search-type` | `kg_graph_search` or `kg_llm_navigation` | from config |
| `--force` | Clear existing data before indexing | off |

```bash
kapso index_kg --wiki-dir ./data/wikis --save-to ./data/indexes/ml.index
kapso index_kg --data-path ./data/kg_data.json --save-to ./data/indexes/kaggle.index
kapso index_kg --wiki-dir ./data/wikis --save-to ./data/indexes/ml.index --force
```

<Note>
  Indexing needs Weaviate and Neo4j running. See [Optional: knowledge-graph backends](/docs/installation#optional-knowledge-graph-backends).
</Note>

## kapso watch

Renders the status of a running `build`, `learn` or `learn_knowledge` operation.

| Argument | What it does | Default |
|----------|--------------|---------|
| `path` | Workspace, status file, or directory of status files. **Required** | — |
| `--json` | Print the status file once, as JSON | off |
| `--follow` | Re-render on each heartbeat until the operation ends | off |
| `--tree` | Show the build's search lineage from its checkpoint, each node with its score, its platform cost and `refused` as the outcome of a cost-refused node when cost-aware selection is on, external baseline comparison, and the knowledge gates it consulted | off |

```bash
kapso watch ./campaign
kapso watch learning/status
kapso watch ./campaign --follow
kapso watch ./campaign --tree
kapso watch ./campaign --json | jq -r '[.state] | @tsv'
```

A campaign writes its status file the moment its workspace is seeded, in phase `setup`, so a watch started right after the launch sees it within seconds. In the seconds before that, `kapso watch` prints one line, `no status yet at <path>`, and exits 1; with `--follow` it prints the line and waits for the file.

### The status file

`--json` prints the file as it is. Every operation (`build`, `learn`, `learn_knowledge`) carries the same core; `build` adds its campaign payload. Fields appear as they are first written, so a reader treats each as optional.

| Field | What it holds |
|-------|---------------|
| `operation` | `build`, `learn` or `learn_knowledge` |
| `phases` | The operation's phases in order. Build: `setup`, `harness_setup`, `lens_planning`, `ideation`, `implementation`, `evaluation`, `verification`, `feedback`. Learn: `harvest`, `mine`, `exam`, `lesson`, `push`. Knowledge: `ingest`, `merge` |
| `state` | `starting` (preparing, for a build the `setup` phase), `running`, `done` or `failed` |
| `phase`, `phase_started_at` | The current phase and when it began |
| `pid` | The writing process. `kapso watch` reports `DEAD` when it is gone |
| `started_at`, `heartbeat_at`, `finished_at` | Timestamps, UTC |
| `heartbeat_seconds` | The writer's beat; `STALLED` after three missed beats |
| `recent` | The last ten human-readable lines |
| `error` | The failure, when `state` is `failed` |
| `budget` | Build: `{elapsed_min, total_min}`, the time dial |
| `iteration` | Build: the iteration in progress |
| `best`, `last` | Build: `{score, node}` of the best and the latest candidate |
| `stopped_reason`, `stop_detail` | Build, at the end: why the campaign stopped |
| `requests` | Build, when `stopped_reason` is `waiting_for_user`: the open inbox requests |
| `platform_budget` | Build, with cost-aware selection on: `{used, budget, unit, refused}` |
| `harness`, `harness_setup` | Build, on a harness: `{name, version, hash, source}`, and `{prepared}` once the setup session ran |
| `trajectory_id`, `bank_head_before`, `cards` | Learn: what is being learned and what the lesson changed |

## kapso inbox

What a paused campaign is waiting on you for, and the reply that resumes it. Inside a campaign directory both forms act on that campaign; elsewhere, name it first. See [the inbox](/docs/build/inbox).

| Form | What it does |
|------|--------------|
| `kapso inbox [CAMPAIGN]` | The open requests of the campaign named, else of the one the current directory is inside, else of every registered campaign that is waiting |
| `kapso inbox reply [CAMPAIGN] [ID] [NOTE]` | Record the reply and resume the campaign in the foreground. The id may be left out when one request is open; an empty note means done |

| Flag | What it does | Default |
|------|--------------|---------|
| `--yes` | Store a reply shaped like a credential anyway. Put it at the end of the line | off |
| `--detach` | Check the reply here, then resume the campaign in a session of its own and return at once with the log and the `watch` command | off |
| `--log` | Where a detached resume's output goes | `<campaign>.log`, beside the campaign directory |
| `--config` | Config whose `inbox.registry` lists the campaigns | packaged `config.yaml` |

```bash
kapso inbox
kapso inbox ./campaign
kapso inbox reply 1 "added the key"
kapso inbox reply ./campaign 1
kapso inbox reply 1 "added the key" --detach
```

## kapso bank

The lesson bank is local-only by default. These two subcommands give it a git remote. Credentials stay with `git` and `gh`; Kapso never handles them.

### kapso bank connect

| Argument | What it does | Required |
|----------|--------------|----------|
| `url` | Git URL of the bank repository, https or ssh | **yes** |

```bash
kapso bank connect https://github.com/your-org/kapso-bank.git
```

### kapso bank create

Creates the GitHub repository with the `gh` CLI, then connects it.

| Argument | What it does | Default |
|----------|--------------|---------|
| `slug` | `org/name` for the new repository. **Required** | — |
| `--public` | Create the repository public | private |

```bash
kapso bank create your-org/kapso-bank
```

## kapso doctor

Reports the requirements your **active config** implies, and exits non-zero when a required item is missing.

| Argument | What it does | Default |
|----------|--------------|---------|
| `verb` | Narrow the report to `research`, `learn_knowledge`, `build`, `learn` or `deploy` | union of all five |
| `--models` | Live-probe each configured CLI and model pair, spending a few one-token calls | off |
| `--config` | Config to check | packaged `config.yaml` |

```bash
kapso doctor
kapso doctor build
kapso doctor build --models
```

See [How do I check my setup?](/docs/installation#how-do-i-check-my-setup) for the output format and what each marker means.

## kapso-mcp

A stdio MCP server for the coding-agent session you work in: the gates Kapso's own sessions get, configured from where the session runs. Not a `kapso` subcommand but a second executable, so a host can name it in a static MCP file.

| Flag | What it does | Default |
|------|--------------|---------|
| `--gates` | Comma-separated gates to serve | `research,repo_memory,experiment_history,bank` |
| `--kg-index` | A `.index` file; adds the `idea` and `code` search gates | — |
| `--config` | Config whose serving, bank and embedding settings apply | packaged `config.yaml` |
| `--root` | The directory the session works in | the current directory |
| `--family` | The task family the bank serves for | the config's `default_mode`, lowercased |

```bash
claude mcp add kapso -- kapso-mcp
codex mcp add kapso -- kapso-mcp
kapso-mcp --gates research,bank --config kapso-config.yaml
```

A gate that cannot be served is named on stderr with its reason; see [Use the gates from your own coding agent](/docs/evolve/mcp-gates#use-the-gates-from-your-own-coding-agent).
